# FetchCatch workspace

FetchCatch stores version-controlled rules as JSON under `.fetchcatch/`. Flows are directed graphs exposed at runtime as `POST /v1/evaluate/{slug}`.

## When to use

- Editing `.fetchcatch/flows/*.json` or `.fetchcatch/response-types/*.json`
- Bootstrapping a workspace (`fcc init`, `fcc login`, `fcc pull`)
- Sync workflow: `fcc status` → `fcc plan` → `fcc apply --dry-run` → `fcc apply`
- Resolving designer vs CLI conflicts (`fcc diff`, `fcc resolve`)
- CI/GitHub Actions sync pipelines
- Flow graph structure questions (nodes, edges, start/end)

## Before editing

1. Read `.fetchcatch/AGENTS.md` if present (generated by `fcc init`).
2. Fetch latest docs from `https://fetchcatch.com/docs/manifest.json` — use the `baseUrl` for raw markdown.
3. Primary agent doc: `https://fetchcatch.com/docs/v0.1/ai-agent-guide.md`
4. Discovery index: `https://fetchcatch.com/llms.txt`

## Workspace layout

```
.fetchcatch/
├── AGENTS.md
├── project.json              # workspace binding — rarely edit
├── sync-state.json           # hash metadata — never edit by hand
├── flows/{slug}.json
├── flows/{slug}.remote.json  # conflict snapshot — read-only
├── response-types/{slug}.json
├── api-sources/
├── auth-profiles/
└── api-keys/
```

## Flow document shape

Top-level fields (`schemaVersion: 1`):

| Field | Notes |
|-------|-------|
| `id` | Stable GUID — **never change** after first server sync |
| `slug` | Matches filename, URL-safe |
| `name` | Display name |
| `graph` | `{ start, nodes[], edges[], viewport? }` |
| `publish` | Default `false`; only set `true` when user explicitly asks to publish |

Node ids must match `^[A-Za-z_][A-Za-z0-9_]*$`.

## Node types

| Type | Purpose |
|------|---------|
| `start` | Entry; optional `inputSchema`, `responseTypeId` |
| `http` | Call OpenAPI operation; requires real `apiSourceId` + `operationId` |
| `condition` | Branch on JSONata boolean; edges need `"when": "true"` / `"false"` |
| `transform` | Store JSONata result in run state |
| `wait_for_event` | Pause until external resume |
| `decision` | Write `responseValues` into typed output |
| `end` | Validate and return final response |

Always add `description` on new nodes explaining intent.

## Task patterns

### Add a branch to a flow

1. Read existing flow JSON and node-type docs.
2. Add nodes with valid ids; wire edges with correct `when` on condition branches.
3. Recommend `fcc plan` (not apply) for user review.

### Add or change a response type

1. Edit `.fetchcatch/response-types/{slug}.json`.
2. Update all dependent `decision.responseValues` in flows in the **same change**.
3. Apply response type before flows if applying separately.

### Set up CI sync

Adapt `https://fetchcatch.com/docs/v0.1/sync-and-ci.md` and the example workflow in the FetchCatch repo at `docs/examples/fetchcatch-sync.workflow.yml`.

Auth: `FETCHCATCH_TOKEN` env var. Set `CI=true` to disable prompts.

## CLI reference

```bash
fcc init --workspace my-workspace
fcc login
fcc pull
fcc status
fcc plan --json
fcc apply --dry-run
fcc apply
fcc diff flows/my-flow.json
fcc resolve flows/my-flow.json --keep-mine|--keep-theirs|--edit
fcc history flows/my-flow.json
fcc rollback flows/my-flow.json --version N
```

### Exit codes (plan/status)

| Code | Meaning |
|------|---------|
| 0 | In sync |
| 1 | Error |
| 2 | Pending changes |
| 3 | Conflicts |

On conflicts: never delete `*.remote.json` and re-apply without inspecting. Use `fcc diff` + `fcc resolve`.

## Hard rules

1. **Never change** resource `id` GUIDs after they exist on the server.
2. **Never fabricate** `apiSourceId` — pull existing flows or ask user to configure API sources in the console.
3. **Do not set** `"publish": true` unless the user explicitly asks.
4. **Do not edit** `sync-state.json` or `~/.fetchcatch/` credentials.
5. **Do not edit** `*.remote.json` conflict snapshots.
6. Validate: one start node, reachable nodes, condition edges have `when`.
7. After edits, recommend `fcc plan` before `fcc apply`.
